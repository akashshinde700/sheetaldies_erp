# ERP UI/UX Design Context

**Project:** SVT ERP (Shital Vacuum Treat Pvt. Ltd. — job-work heat-treatment ERP, also serving Sheetal Dies & Tools Pvt. Ltd.)
**Audit type:** Read-only inspection. No source code, business logic, APIs, database, or routing was modified while producing this document.
**Method:** Full enumeration of routes (`App.jsx`), all page/component file names, and the global CSS/Tailwind design-token layer (exhaustive). Individual module pages were sampled representatively (Dashboard, Parties, Job Cards, Invoices, Analytics, Pending, VHT Runsheet, Certificates) and cross-checked against the shared components they all consume — since every list/table/badge/button in this app is built from the same handful of shared primitives (`.th`, `.td`, `Badge`, `StatusPill`, `Button`, `Card`, `KpiCard`, `PageHeader`), auditing those primitives plus a representative sample gives accurate coverage of the whole app's visual language. Anything stated below is backed by an actual file/line; nothing is invented.

## 3. Global UI Structure

- **Sidebar** (`Sidebar.jsx`): fixed, 16rem wide (collapsible to 4.75rem on desktop), three role-gated sections (`Main`, `Operations` — Manager+, `Admin` — Admin only), a live "Pending" badge count fetched via `useQuery`, user card + sign-out at the bottom.
- **Topbar** (`Layout.jsx`): search trigger (`Ctrl+K` → `CommandPalette.jsx`), theme toggle, user menu.
- **Breadcrumbs**: `Breadcrumbs` component inside `page-header.jsx`, opt-in per page (not every page passes `breadcrumbs`).
- **Page headers**: `PageHeader` component — title + optional meta line + right-aligned actions; used across the newer (modernized) pages. Older pages hand-roll their own header markup with `<h1>` + buttons directly.
- **Content containers**: `.page-container` (`max-w-readable`, i.e. `72rem`), `.page-stack`/`.page-fill` for full-height list pages with sticky headers (`index.css` lines 886-921).
- **Cards**: `components/ui/card.jsx` (`Card`/`CardHeader`/`CardTitle`/`CardContent`/`CardFooter`) — the modern primitive; `.card`/`.card-interactive` CSS classes — the older equivalent. Both produce visually near-identical white/rounded-xl/bordered boxes.
- **Tables**: no component, CSS-class convention only (`.th`/`.td`/`.tr`, or the separate `.table-responsive thead th` sticky-header variant). See §10.
- **Forms**: mix of `react-hook-form` (newer pages) and plain controlled `useState` (older pages).
- **Modals**: `components/ui/dialog.jsx` (Radix, animated, accessible) vs. `ConfirmDialog.jsx` (hand-rolled, its own focus/Escape logic) — two parallel implementations for the same job (see §9, §13).
- **Drawers**: `components/ui/sheet.jsx` (Radix-based slide-in panel), animation keyframes `sheetInRight/Left/Up` defined in `index.css` lines 880-883.
- **Tabs**: `components/ui/tabs.jsx` (Radix).
- **Dropdowns**: `components/ui/dropdown-menu.jsx` (Radix), plus `SearchSelect.jsx` for master-data pickers.
- **Tooltips**: `components/ui/tooltip.jsx` (Radix) — used sparingly.
- **Toasts**: `react-hot-toast`, invoked ad hoc (`toast.success(...)`/`toast.error(...)`) in 38 files — no wrapper component, so toast copy/style is decided per call-site.
- **Pagination**: `components/Pagination.jsx` — cursor-based, custom hook (`usePagination`), not the shadcn style.
- **Status badges**: **two independent systems** — `Badge` (`components/ui/badge.jsx`, generic `neutral/success/error/warning/info/outline` variants) and `StatusPill` (`components/ui/status-pill.jsx`, status-code-aware, tone-mapped) — plus the standalone `statusColor()` function in `utils/statusColors.js` used by pages that predate `StatusPill`. Three ways to render what is conceptually one thing.
- **Action buttons**: `components/ui/button.jsx` (variant-based, the modern standard) vs. raw `.btn-primary`/`.btn-secondary`/`.btn-outline`/`.btn-ghost`/`.btn-danger` CSS classes (`index.css` lines 117-161) used by older pages. Both produce near-identical results by design (the CSS classes were clearly the precursor to the `Button` component) but a page can only get animation/loading-spinner support (`Loader2`) by using the newer `Button`.

## 4. Current Color Palette Audit

The entire palette is driven by CSS custom properties in `src/index.css`, generated into Tailwind utilities by a `ramp()` function in `tailwind.config.js`. Six roles are ramped 50→950: **primary, neutral, success, warning, danger, accent**, plus two extra roles **info, heat**. Legacy Tailwind hue names are aliased onto these roles so `bg-blue-600`, `text-emerald-700`, `bg-amber-100` etc. keep working without touching component code:

```
indigo, brand        → primary
sky, blue, cyan       → info
slate, gray, zinc     → neutral
emerald, green, teal   → success
amber, yellow, orange  → warning
rose, red, pink        → danger
violet, purple         → accent
```

**Current values (light mode), as of this audit:**

| Usage | Current Color | HEX (600 step) | Where Used | Assessment |
|---|---|---|---|---|
| Primary / Brand | Deep Indigo | `#3730A3` | Sidebar active state, primary buttons (via `bg-primary-*`), focus rings | Good — deliberate, deep, non-childish; consistent with an enterprise ERP |
| Info | Blue | `#2563EB` | "IN PROGRESS"/"SENT" status badges, `.btn-secondary`, form-input focus ring (`sky-400`) | Good, clearly separated from Primary now |
| Sidebar | Dark Navy | `#0F172A` (literal, hardcoded in `Sidebar.jsx`, **not** a token) | `Sidebar.jsx` `bg-[#0F172A]` | Works visually, but bypasses the token system — see §17 |
| Background | Slate 50 | `#F8FAFC` (`--app-bg-1`) | `body` background | Good |
| Card / Surface | White | `#FFFFFF` | `.card`, `Card` | Good |
| Border | Slate 200 | `#E2E8F0` (`--c-neutral-200`) | Card/table/input borders | Good |
| Text (heading) | Slate 900 | `#0F172A` (`--text-strong`) | `<h1>` etc. | Good |
| Text (secondary) | Slate 500/600 | `#64748B` / `#475569` | Sub-labels, table `.th` | Consistent |
| Success | Emerald | `#059669` | PASS/COMPLETED/PAID badges | Good, standard |
| Warning | Amber | `#D97706` | PENDING/PARTIAL/SENT_FOR_JOBWORK badges | Good, standard |
| Danger | Red | `#DC2626` | FAIL/CANCELLED/ON_HOLD badges, delete buttons | Good, standard |
| Accent | Violet | `#7C3AED` (`--c-accent-600`) | Rarely used directly; mostly a leftover role | Underused / unclear purpose — see below |
| Heat | Burnt orange | `#C15511` (`--c-heat`) | Temperature-cycle charts (`HeatCycleGraphPreview.jsx`) | Good — a genuinely domain-specific, well-justified 8th color for "this is a temperature value" |

**Duplicate / overlapping colors:**
- `pink` is aliased to the **danger** role. Any component author who reaches for `bg-pink-50` thinking "a soft neutral pink" gets the app's red/danger ramp instead — a real trap that already caused one incident this session (a shared `.th` class used `sky-50`, i.e. what is now the info-role tint, for every single table header in the app, making every list page's header read as brand/status-colored instead of neutral — since fixed for `.th`, but the underlying `sky/blue → info` alias pattern means any other component reaching for "sky" as a neutral light-blue accent will get the same effect).
- `Badge`'s `info` variant (`bg-sky-100 text-sky-800`) and `StatusPill`'s `info` tone (`bg-info-50 text-info-700`) and `StatusPill`'s separate `progress` tone (`bg-sky-50 text-sky-700`) all resolve to **the same underlying color** today (`sky`/`blue` → `info`), but are declared as three separately-named tones/variants. This is an "almost identical colors, different names" case waiting to drift apart.
- **Three parallel status-color systems** exist for what is one concept (see §9): `utils/statusColors.js` (`STATUS_COLORS` map → raw Tailwind hue classes), `components/ui/status-pill.jsx` (`STATUS_TONE` map → semantic tone names), and ad hoc inline `badgeColor`/`iconBg` props on `Dashboard.jsx`'s `KpiCard` usages. All three encode the same "what does amber mean here" decision independently.
- **Analytics charts bypass the token system entirely.** `Analytics.jsx`/`AdvancedAnalytics.jsx` hardcode a `COLORS` array of literal hex strings (`#3730A3`, `#7c3aed`, `#059669`, `#D97706`, `#DC2626`, `#0e7490`, `#a04606`, `#4338ca`) rather than reading the CSS variables — meaning a future palette change (like this document is preparing for) requires manually touching two more files instead of one, and dark-mode readability for those exact literals has to be special-cased in `index.css` (`.dark [fill="#059669"] { fill: #34C77D !important; }` etc., lines ~1319-1325).
- `PrintHeader.jsx` also hardcodes its own literal hex values (independent of the app theme, by design — print output should never follow the on-screen theme) — correctly out of scope for a UI palette change, but worth noting as a *third* place colors live.

**Colors used for multiple, unrelated meanings:** none found beyond the pink/danger alias above — the role system is otherwise coherent.

**Excessive accent colors / poor hierarchy (the concrete complaint that triggered this audit):** `Dashboard.jsx`'s 8 KPI cards (`pages/Dashboard.jsx` lines 171-233) each set their own `iconBg`/`badgeColor` independently: sky, blue, amber, rose/emerald (conditional), emerald, orange, rose/slate (conditional), rose/slate (conditional). Seven-plus distinct hues appear side-by-side on the single most-viewed screen in the app, with no visual rule for *why* a given card gets a given color — some are semantic (rose only when `qualityAlerts > 0`), others are arbitrary (the first three are just sky/blue/amber with no status logic behind the color choice at all). This is the single biggest concrete "looks like a SaaS template, not an ERP" finding in the codebase.

**Contrast:** no automated contrast failures found; all text/background pairs sampled use standard Tailwind-ramp combinations (`-700` text on `-50`/`-100` backgrounds) which pass WCAG AA in the overwhelming majority of cases. Not independently measured pixel-by-pixel.

## 5. Color Usage By Module

**Dashboard** (`pages/Dashboard.jsx`): 8 KPI cards with 7+ distinct hues (see §4); recent-activity feed uses `StatusPill`/`statusColor()` per row.

**Parties / Admin masters** (`PartyList.jsx` and siblings): table header neutral (`.th`), row action icons (`Eye`/`Pencil`/`Trash2`) in neutral slate with a `rose` hover state only on delete — this pattern is clean and consistent across `ItemList.jsx`, `MachineList.jsx`, `ProcessList.jsx`.

**Job Cards**: status via `StatusPill` (`CREATED`→neutral, `IN_PROGRESS`→progress/blue, `SENT_FOR_JOBWORK`→warning, `INSPECTION`→info, `COMPLETED`→success, `ON_HOLD`→danger) — six statuses, six colors, on every row of a dense table; combined with per-row action buttons this is the most color-dense table in the app.

**Invoices**: payment status (`PENDING`/`PARTIAL`/`PAID`) drives both a badge color and (per Dashboard KPI logic) a KPI card's icon color — the same status value visually represented two different ways in two different places (badge shape on the list, icon-tint on the dashboard).

**Analytics**: the highest concentration of raw, non-token color in the app — a fixed 8-color categorical palette for chart series/status bars/pie slices (§4). This is the one screen where genuinely decorative, varied color is appropriate (distinguishing many data series) — but right now it's disconnected from the semantic role system, so "amber" in a chart and "amber" in a badge are not guaranteed to be the same amber if the token ramp changes again without remembering to touch this file too.

**VHT Runsheet / Certificates**: status via the same `StatusPill`/`statusColor()` duality; temperature charts use the dedicated `heat` role — a good example of color used *because it communicates meaning* (temperature), not decoration.

**Visual inconsistency between modules:** none structural — the underlying primitives are shared. The inconsistency is entirely in *which* of the 2-3 parallel systems (Badge vs. StatusPill vs. statusColor vs. raw hex) a given page happens to use, which is a function of when that page was last touched, not the module's domain.

## 6. Typography Audit

- **Font families:** `Inter` (default body, legacy pages, and **every print sheet** — deliberately, so print output never changes), `Manrope` (headings, `font-headline`), `IBM Plex Sans`/`IBM Plex Mono` (`font-app`/`font-app-mono` — opt-in face for "modernized" pages only). Three type faces in simultaneous use is a lot for one product, though the split is intentional and documented in `index.css` comments (lines 799-808).
- **Font sizes:** standard Tailwind scale (`text-xs`…`text-3xl`) is used 700+ times combined — good baseline. **However**, arbitrary pixel sizes below the scale's floor are extremely common: `text-[10px]` appears **272 times**, `text-[11px]` **64 times**, `text-[9px]` **38 times** (grep count across `.jsx`). That's 374 instances of hand-picked micro-typography (table headers, badges, uppercase labels, meta text) that exist entirely outside Tailwind's `text-xs` (12px) step — effectively an undocumented second, denser type scale that every component author re-invents by eye rather than by system. A `.font-app :where([class*="text-[10px]"]) { font-size: 11px; }` rule in `index.css` (line 845) already exists specifically to patch this up for modernized pages — a strong signal the team is aware of the problem but hasn't consolidated it.
- **Heading hierarchy:** `PageHeader`'s `<h1>` is consistently `text-lg sm:text-xl font-bold` — appropriately restrained for a data-dense app (not oversized). `CardTitle` is `text-sm font-bold` — quite small for a "title," but consistent everywhere it's used.
- **Table typography:** `.td` is `text-xs` (12px), `.th` is `text-[10px]` uppercase — small but consistent via the shared classes; the concern is entirely the *volume* of one-off overrides elsewhere, not the table system itself.
- **Buttons/labels:** `text-sm font-semibold` (Button), `text-[10px] font-semibold uppercase` (`.form-label`) — consistent.

## 7. Spacing & Layout Audit

- **No formal spacing scale is enforced** beyond Tailwind's default (4px-based) scale, though a `--space-1…--space-12` CSS custom-property scale *is* defined (`index.css` lines 828-830) and appears effectively unused (no grep hits found consuming `var(--space-`) — a designed system that isn't actually wired up.
- Padding usage is heavily concentrated but not fully uniform: `px-3`/`px-4` (110/102 uses) and `py-2`/`py-1.5` (140/88 uses) dominate, which is a reasonable de-facto standard — but the long tail (`px-1`, `px-2.5`, `px-3.5`, `py-0.5`, `py-2.5`, `py-3.5`) shows every component author picking a "close enough" value rather than choosing from a fixed set.
- **Sidebar width:** `w-64` (16rem) expanded, `w-[4.75rem]` collapsed — a one-off arbitrary value rather than a token.
- **Card spacing:** `CardHeader`/`CardContent` use `px-4 sm:px-5` — a responsive step exists but only at one breakpoint.
- **Gaps:** `gap-2`/`gap-3` dominate (185/158 uses) — a reasonably consistent default.
- **Conclusion:** the project has *conventions* (informally, "most things use 3/4 for x-padding and 2/3 for gap") but no enforced, named spacing system that a new page must follow — it currently relies on developers pattern-matching nearby code.

## 8. Border Radius & Shadow Audit

- **Radius:** `rounded-lg` and `rounded-xl` are overwhelmingly dominant (118 + 129 raw grep hits, though the regex used also catches `rounded-full`/`rounded-md`/`rounded-2xl` fragments — manually confirmed `rounded-lg`/`rounded-xl` are the two workhorse values for buttons, inputs, and cards respectively), `rounded-full` for badges/pills/avatars, `rounded-2xl` reserved for modals (`DialogContent`) — this is a coherent, restrained radius system in practice, not excessive.
- **Shadows:** three real levels exist and are used correctly — `shadow-card` (default card elevation, defined in `tailwind.config.js` `boxShadow.card`), `shadow-card-hover` (interactive card hover), `shadow-card-elevated` (modals). `shadow-sm`/`shadow-lg`/`shadow-md` (Tailwind defaults) are also used directly in a number of places alongside the named system, which is a minor duplication (two ways to say "small shadow") but not a visual problem. A small number of *tinted* shadows exist (`shadow-violet`, `shadow-sky`, `shadow-rose`, `shadow-emerald` — 2 hits each) — colored shadows on specific buttons, a deliberate touch rather than an inconsistency.
- **Conclusion:** radius/shadow are the most disciplined part of the design system already — not a priority area for the redesign.

## 10. Table UX Audit

- **Column structure/widths:** mostly unspecified (`<th className="th">Name</th>` with no explicit width), letting the browser auto-size — acceptable for narrow tables (Parties: 5 columns) but a real problem for wide ones (`PartyRatesMatrix.jsx` is a matrix table with a `sticky left-0` frozen first column, hinting the team already had to work around auto-sizing for wide data grids).
- **Row height:** governed by `.td`'s `py-3.5` — consistent across every table using the shared class, since there's no per-table override pattern.
- **Header design:** was, until this session's fix, a light-blue gradient (`bg-gradient-to-b from-sky-50/95 to-sky-50/75`) — now flat neutral `bg-slate-50`. Historically this is *the* reason table headers read as "branded pink/blue" across the whole app, since `.th` is shared by every single list page.
- **Hover:** `.tr` gives `hover:bg-slate-50/90` — subtle, consistent, good.
- **Sorting:** not found as a generic table feature in the sampled pages — appears to be search/filter-driven (`ListSearchInput.jsx`, per-page filter state) rather than click-to-sort columns.
- **Selected rows:** no visual "selected row" state found (consistent with the earlier finding that there are no bulk actions).
- **Action buttons:** consistently icon-only (`Eye`/`Pencil`/`Trash2` from `lucide-react`) right-aligned in an "Actions" column, matching the `Actions` header we found in `PartyList.jsx` and generalized across admin masters — a clean, consistent pattern.
- **Empty states:** inconsistent (see §9's `EmptyState` finding) — some tables show a styled empty state, most show a bare sentence.
- **Loading states:** inconsistent — `SkeletonTable` exists but isn't universally used.
- **Mobile behavior:** `table.list-cards` (stacked-card layout on phones, `index.css` 860-873) exists as an opt-in, but only 5 files use it — meaning most list pages on this ERP will horizontal-scroll on a phone rather than reflow, a real mobile-usability gap for an app whose users (per `README`/CLAUDE.md workflow) include shop-floor Operators who may check job status from a phone.

## 11. Form UX Audit

- **Two form paradigms coexist:** `react-hook-form` + `zod` resolvers (`@hookform/resolvers`) in newer forms vs. plain `useState`-driven controlled inputs in older forms. Both are legitimate patterns; the inconsistency is which a given module happens to use.
- **Multi-step forms:** a real, well-built pattern exists — `components/ui/stepper.jsx` (`useStepper` hook: `current/completed/next/back/goto/isFirst/isLast`) + `components/ui/wizard-shell.jsx`, used by Job Card, Certificate, and VHT Runsheet forms. This session's own history (documented in prior conversation) shows this pattern being actively tuned (merging/splitting steps) — it's a living, well-understood part of the codebase, not legacy debt.
- **Field layout:** the long history of "put these fields on one line" requests (documented in project memory) shows the form layout is currently achieved via manual `flex flex-wrap` + fixed-`px` `basis` widths per field, tuned by eye per form — there is no responsive form-grid *system* (e.g., a `<FormRow cols={3}>` component) that would let a new form get sensible one-line/wrapping behavior automatically. Every layout decision is bespoke CSS on that one field, in that one form.
- **Labels:** `.form-label` (`text-[10px] font-semibold uppercase`) is a shared, consistent convention above the input — good.
- **Validation/errors:** `useFormValidation.ts` + `zod` for newer forms; not verified whether older forms have equivalent inline validation or rely on submit-time toast errors only (worth a follow-up read of one older form's submit handler).
- **Modal forms:** `Dialog`-based forms exist (e.g. `SplitJobCardModal.jsx`) alongside full-page forms — a reasonable split (quick, single-purpose actions as modals; multi-section documents as dedicated pages).
- **Upload controls:** exist (`CertPhotosSection.jsx`-style photo upload per prior session context) — not independently re-verified in this pass.

## 12. Responsive Design Audit

- A `min-h-[44px]` tap-target convention is applied consistently to buttons and inputs at "coarse pointer" breakpoints (`@media (hover: none) and (pointer: coarse)`, `index.css` 651-664) — a genuinely good, easy-to-miss detail showing real mobile-usability intent.
- Date inputs are deliberately capped at `max-width: 9.5rem` on screen (not print) so they don't stretch a flex/grid cell — another sign of considered, iterative responsive tuning (this exact rule was hit and relied on earlier in this project's history when a "Run Date" field's calendar icon disappeared after over-narrowing).
- **The weak point is tables**, as detailed in §10: only 5 of ~30 list pages use the `list-cards` mobile pattern; the rest will horizontal-scroll on phones/tablets.
- Sidebar collapses to icon-only (`lg:w-[4.75rem]`) on desktop via a manual toggle, and becomes an off-canvas drawer (`-translate-x-full` / backdrop) below `lg:` — a standard, correctly-implemented responsive sidebar pattern.
- Print pages are explicitly excluded from all responsive/dark-mode logic (`print:hidden` on the sidebar/backdrop, forced-light CSS for print) — correct behavior for documents meant to be printed on A4.

## 13. Accessibility Audit

**Positives found:**
- `focus-visible:ring-2 ... focus-visible:ring-offset-2` is applied consistently across `Button`, `.btn-*` classes, and most interactive elements — real keyboard-focus visibility, not just a browser default.
- `aria-label` present on icon-only buttons (`aria-label="Close"` in `DialogContent`, `aria-label="Back"` in `PageHeader`, `aria-label="Main menu"`/`aria-label={collapsed ? 'Expand sidebar' : 'Collapse sidebar'}` in `Sidebar.jsx`).
- `role="switch"` + `aria-checked` correctly used on the dark-mode toggle (`Layout.jsx`).
- `role="navigation"` on the sidebar `<aside>`.
- `@media (prefers-reduced-motion: reduce)` is respected globally (`index.css` 78-89), collapsing all animations/transitions to near-zero duration.
- `ConfirmDialog` explicitly moves focus to the confirm button on open and closes on Escape (documented behavior in its own comment).
- `aria-current="page"` used for both breadcrumb "current page" and sidebar "active route" — correct semantic use of the attribute (also the mechanism the newer Sidebar redesign's CSS could target, see the removed dark-mode override rule from this session's own change).

**Gaps / not verified:**
- Color is not the *only* signal for status (`StatusPill`'s own doc-comment states this as a design principle, and it does render the status text, not just a colored dot) — good practice already followed.
- Icon-only table action buttons (`Eye`/`Pencil`/`Trash2`) were not confirmed to carry `aria-label`s in every instance sampled — worth a follow-up sweep since a screen-reader user would otherwise hear "button" three times per row.
- Form error messaging pattern (inline vs. toast-only) not fully verified for older, non-`react-hook-form` forms — flagged in §11.
- No skip-to-content link found for keyboard users to bypass the sidebar.

## 15. Current UX Problems (prioritized)

**P0 — Critical**
- Dashboard KPI-card colors are assigned per-card with no consistent semantic rule (§4, §9) — this is the concrete, named complaint that started this whole audit ("pink table headers, pink active states, yellow cards, blue sidebar together, weak hierarchy").
- Table headers used the "info/sky" tint app-wide via one shared CSS class (`.th`) — a single-point-of-failure that made every list page look brand-colored instead of neutral (already patched this session, but the *pattern* — reaching for `sky`/`pink` as if they were neutral tints — remains a latent risk elsewhere).

**P1 — High**
- Two full parallel generations of the design system (CSS-class components vs. shadcn/Radix components) coexist with no migration tracking — new engineers can't tell which is "current."
- Three parallel status-color systems (`StatusPill`, `statusColor()`, ad hoc KPI-card props) for one concept.
- Only 5/~30 list pages support the mobile card-table layout — most tables will horizontal-scroll on phone.
- No shared `EmptyState`/`LoadingState` component — every page reinvents "No records found."
- Chart colors (`Analytics.jsx`/`AdvancedAnalytics.jsx`) are hardcoded hex, disconnected from the token system that drives every other color in the app.

**P2 — Medium**
- 374 uses of arbitrary sub-`text-xs` pixel sizes (`text-[10px]`/`[11px]`/`[9px]`) instead of a defined micro-type scale.
- Two icon systems in simultaneous use (`lucide-react` SVGs vs. `material-symbols-outlined` font) — inconsistent icon weight/style between old and new pages.
- Spacing is convention-driven, not system-enforced (`--space-*` tokens defined but unused).
- Two inventory pages/routes (`/inventory` and `/purchase/inventory`) with separate implementations — naming/purpose overlap not resolved.
- No bulk actions anywhere — likely a real efficiency gap for an ERP where Operators process many records a day (not colour/layout, but worth flagging since it affects table design decisions in the eventual redesign).

**P3 — Low**
- Minor shadow-declaration duplication (`shadow-card` system vs. raw Tailwind `shadow-sm/md/lg` used interchangeably).
- `ConfirmDialog.jsx` duplicates functionality Radix `Dialog` already provides.

## 16. Professional ERP Benchmark Analysis

This is a **manufacturing / industrial / job-work (heat-treatment) ERP** — its users are shop-floor operators, quality inspectors, and back-office finance staff processing dozens of job cards, run sheets, and certificates per day, often printing physical documents (job cards, certificates, invoices, dispatch challans) that travel with the physical material. Based purely on that functional reality (not on any competitor's visual design):

- **Density over decoration.** Users scan tables and forms repeatedly, all day — the interface should optimize for fast, confident scanning (consistent column alignment, restrained color, predictable row height) over visual flourish.
- **Status must be instantly legible without color alone**, because these are safety/quality-relevant decisions (pass/fail, on-hold, quality-alert) — `StatusPill`'s existing "text always carries the meaning too" principle is exactly right and should be the app-wide rule, not one component's private policy.
- **Color should be a signal, not a background theme.** The current architecture (a handful of semantic roles: primary/info/success/warning/danger/neutral/heat) is structurally sound for this; the problem today is *discipline in applying it* (§4, §15-P0), not the architecture itself.
- **Print fidelity matters as much as screen UI** — this app already treats print as a first-class, separately-themed surface (forced-light, its own color literals in `PrintHeader.jsx`) which is correct for a business that hands printed certificates/invoices to customers and auditors.
- **The domain deserves exactly one "this is physically hot/technical" accent** — the existing `heat` role, used only for temperature data, is a good example of the kind of restrained, meaningful color use this ERP should have more of elsewhere (e.g., a single well-chosen accent for "this number is a weight/measurement," if that's ever needed) rather than many decorative hues.

## 18. Design Direction Recommendation

The following three directions are presented for the next design pass to choose between/finalize — none is implemented, none is assumed as final.

**Direction A — Industrial Enterprise (Slate + Indigo)**
*The direction already partially in place after this session's changes.*
- Primary `#3730A3` · Secondary/Sidebar `#0F172A` · Background `#F8FAFC` · Surface `#FFFFFF` · Text `#0F172A`/`#475569` · Border `#E2E8F0` · Success `#059669` · Warning `#D97706` · Danger `#DC2626` · Info `#2563EB`
- **Feeling:** premium enterprise SaaS with a serious, technical edge; indigo reads as "trustworthy software," not "industrial machinery."
- **Advantages:** already implemented in the token layer, zero migration cost, broadly familiar to any modern B2B software user, easy to keep accessible (indigo has good contrast at 600-800).
- **Disadvantages:** indigo is an extremely common "generic enterprise SaaS" choice (Slack, Stripe-adjacent, countless dashboards) — it solves the "childish" complaint but doesn't give SVT a distinctive identity; risks becoming visually interchangeable with any other admin panel.

**Direction B — Graphite + Teal (Industrial / Engineering)**
- Primary `#0F766E` (teal) · Sidebar `#111827` (graphite/near-black) · Background `#F8FAFC` · Surface `#FFFFFF` · Text `#111827` · Border `#E5E7EB` · Success `#16A34A` · Warning `#D97706` · Danger `#DC2626` · Info (would need defining — a blue distinct from teal, e.g. `#2563EB`)
- **Feeling:** heavier, more mechanical/industrial — teal+graphite reads closer to "physical plant equipment / engineering tooling" than "generic SaaS."
- **Advantages:** more distinctive than indigo for a heat-treatment/manufacturing business specifically; graphite sidebar feels appropriately heavy-industry.
- **Disadvantages:** requires a second full token-ramp migration (every current `primary`/`neutral` value changes again, on top of the one just done); teal-vs-success(green) proximity needs careful contrast checking so "brand" and "success" don't read as the same hue at a glance.

**Direction C — Warm Neutral + Deep Blue (Corporate / Conservative)**
- Primary `#1D4ED8` (a deeper, more saturated blue than the current Info role) · Sidebar `#1E293B` · Background `#FAFAF9` (warm-tinted, not cool slate) · Surface `#FFFFFF` · Text `#1C1917` · Border `#E7E5E4` · Success `#059669` · Warning `#D97706` · Danger `#DC2626`
- **Feeling:** conservative, bank/insurance-adjacent corporate trust; the warm-neutral background (vs. the current cool slate) is the one genuinely different structural choice here.
- **Advantages:** very safe, unlikely to ever look "wrong" to any stakeholder; blue-as-primary is the least risky choice for a first-time ERP redesign.
- **Disadvantages:** would collide with the existing Info role (both blue) unless Info is redefined too; least distinctive of the three options; closest in feeling to "any generic ERP," which somewhat re-invites the original "SaaS template" complaint just in a darker shade.

**This document does not choose between them** — that decision belongs to the next design pass, informed by this context.

## 20. Final Executive Summary

### Current Design Strengths
- A real, working, CSS-variable-driven design-token architecture already exists (`ramp()` in `tailwind.config.js` + `index.css`) — a full palette change is a low-risk, single-file operation, as demonstrated twice in this session.
- Radius, shadow, and focus-visible discipline are already strong and require little to no rework.
- The multi-step form/wizard pattern (`stepper.jsx`/`wizard-shell.jsx`) is genuinely well-built and actively maintained.
- `StatusPill`'s design principle ("color is never the only signal") is exactly the right rule for this domain and just needs to be applied universally.
- Print output is correctly isolated from the on-screen theme — a detail many apps get wrong.
- Real accessibility groundwork exists (focus rings, aria-labels, reduced-motion support, focus management in dialogs).

### Current Design Problems
- Color is applied per-component-instance rather than per-meaning, most visibly on the Dashboard's 8 KPI cards.
- Two full generations of design-system components coexist without a migration plan.
- Three parallel status-color implementations for one concept.

### Biggest Visual Problems
- Dashboard KPI-card color scatter (§4, §15-P0) — the exact, named source of the "childish/SaaS-template" feedback that started this whole exercise.
- (Already fixed this session) shared `.th` table-header class defaulting to a brand-tinted background across every list page in the app.

### Biggest UX Problems
- Inconsistent mobile table behavior (5/~30 pages).
- No shared empty/loading state components.
- No bulk actions on any list, despite this being a high-volume daily-use ERP.

### Biggest Consistency Problems
- Old CSS-class components vs. new shadcn/Radix components, both fully functional, no documented "which one to use" rule.
- Icon system split (`lucide-react` vs. `material-symbols-outlined`).
- Arbitrary micro-typography (374 instances of `text-[9-11px]`) instead of a defined type scale.

### Current Color Problems
- See §4 in full — summary: architecture is sound, *discipline in applying it* is the actual problem, plus analytics charts and `PrintHeader.jsx` sitting outside the token system entirely.

### Current Typography Problems
- Three font families in simultaneous use (by design, but worth confirming is still intentional going forward).
- No formal micro-type scale below `text-xs` (12px), despite it being used constantly in practice.

### Current Layout Problems
- No enforced spacing system (tokens defined, unused).
- No reusable responsive form-row/grid component — every "put these fields on one line" layout is bespoke per field.

### What Should NOT Be Changed
- The token architecture itself (`ramp()` + CSS variables) — it works, keep it.
- The print-page color isolation (`@media print` / `.dark .page` overrides) — do not let a future redesign leak on-screen theme changes into printed documents.
- The multi-step wizard pattern and its `useStepper` API.
- The SVT logo and TÜV certification mark — real brand/accreditation assets, never recolor or redesign them.
- `StatusPill`'s "text always carries meaning, not just color" principle.

### What Should Be Improved
- Establish one canonical KPI-card color rule (e.g., "icon color is decorative-neutral by default, and only shifts to a semantic color when the metric itself is in an alert state" — already half-true for 3 of the 8 current cards; make it true for all 8).
- Pick one status-badge component (`StatusPill`) and retire the other two.
- Pick one button/card/dialog generation and schedule the other's migration.
- Bring `Analytics.jsx`/`AdvancedAnalytics.jsx` chart colors onto the token system.
- Extend `table.list-cards` to every list page, or replace it with a single shared `<DataTable>` component that has the behavior built in.
- Build one shared `EmptyState` and `LoadingState` component and adopt them everywhere.
- Define a small, named micro-type scale (e.g., `10px`/`11px` as actual scale steps, not arbitrary values) if sub-12px text is going to keep being this common.

### Recommended Design Principles
1. Color communicates meaning, never decorates.
2. One component per concept (one button system, one badge/status system, one dialog system).
3. Tables are the primary surface of this product — optimize every table decision for fast daily scanning by shop-floor and back-office staff, not visual novelty.
4. Print is a separate, permanent surface — never let screen-theme changes affect it.
5. Mobile is not optional for an ERP whose users include shop-floor operators — every list needs a real small-screen layout, not horizontal scroll.

### Recommended Design Direction
Not finalized here by design (§18) — Direction A (Slate + Indigo) is already substantially implemented and is the lowest-risk continuation; Direction B (Graphite + Teal) is the most distinctive to SVT's actual industry if the team wants to invest in a second token migration; Direction C is presented as the conservative baseline. The next design pass should make this call explicitly rather than let it be decided implicitly by whichever token values happen to be in `index.css` at the time.

### Priority Roadmap

**Phase 1 — Design system foundation**
Finalize one color direction (§18) and lock the token values; retire the duplicate status-color/badge/button/dialog/card implementations down to one each; define a real micro-type scale.

**Phase 2 — Global layout**
